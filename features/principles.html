Principles

Overview

These principles apply to all Player Experience work. The UX principles are non-negotiable quality gates for any flow, proposal, or recommendation. The UI principles govern layout and interaction so that lower-complexity, well-trodden changes can be made consistently and safely.

Where a change can be made within these principles and the per-feature guidance, it is in scope. Where it cannot — a new component, a new region, a new interaction pattern, or anything these pages don't already cover — it should be taken to design rather than invented.

UX principles

13 non-negotiable rules. Cross-check every screen against these; where a principle conflicts with a specific market regulation, the regulation wins — but document the conflict.

1Document the logic first

  • Code is law: design artifacts must map directly to the strict text of the regulation.
  • Traceability is key: every field, checkbox, and tooltip must link back to a specific legal requirement.
  • No rogue features: avoid unrequested "delighters" that might accidentally violate compliance.

2Don't over-optimise for frictionless flow

  • Friction is a feature: speed causes user errors, which lead to compliance breaches.
  • Intentional speedbumps: use explicit confirmation for irreversible legal actions.
  • Forced reading works: make users scroll to the bottom of critical disclosures before enabling buttons.

3Clear beats clever every time

  • Ban technical jargon: translate complex legal mandates into universal, plain language.
  • Eliminate ambiguity: use absolute terms like "Required" instead of subtle visual hints.
  • No clever UI patterns: avoid micro-animations or trendy layouts that might confuse vulnerable users.

4Design for the "worst-case" data scenario

  • Stress-test the layout: design for the longest possible legal names, error states, and disclaimers.
  • No text truncation: important compliance text must never be hidden behind an ellipsis.
  • Flexibility is required: layouts must scale gracefully when dynamic, localised legal text shifts in length.

5Accessibility is non-negotiable

  • Compliance means WCAG: treat accessibility (WCAG 2.2 or current regional standards) as a legal mandate.
  • Check the basics: enforce colour contrast, logical screen-reader order, and full keyboard navigation.
  • No colour-only indicators: never convey error or success using colour alone.

6Make system status absolute

  • Concrete receipts: give unambiguous confirmation when a regulatory step is done.
  • Explicit audit trails: log exactly what the user saw, clicked, and agreed to, with timestamps.
  • Clear error paths: tell users exactly why a submission failed and how to fix it.

7Never use dark patterns

  • Opt-in by default: keep data-sharing, marketing, and optional-agreement checkboxes unchecked.
  • Equal-weight UI: "Cancel" / "Opt-out" has the same visual prominence as "Accept".
  • Honest microcopy: labels describe the action ("Authorise Payment", not "Continue").

8State management is everything

  • Map every edge case: expired sessions, partial saves, connectivity drops, rejected states.
  • Auto-save safely: don't lose user data in long forms, but mask sensitive data (PII) on session timeout.

9Progressive disclosure for complex regulations

  • Layer legal information: summary first, detail on demand (expandable sections, info icons, "learn more").
  • Exception: if the regulation requires the user to have seen the full text first (e.g. T&Cs), use the forced-reading pattern from principle 2.

10Contextual timing over preemptive walls

  • Surface compliance interventions at the moment of relevance, not as a pre-login gate unless legally required.
  • Show deposit-limit warnings when the user is about to deposit, not on app launch. Interceptors are guardrails, not roadblocks.

11Preserve user agency within legal bounds

  • Always give a path forward. If they can't do X, clearly explain what they can do.
  • Never present a dead-end screen without an action (even if it's "contact support" or "come back on [date]").
  • Frame limitations as protection, not punishment.

12Consistent mental models across journeys

  • A concept that appears in multiple places (e.g. a limit) must look and behave identically — same component structure, same copy tone.
  • Users shouldn't learn a new interaction pattern for the same concept in a different context.

13Localisation as a first-class concern

  • Design every screen assuming copy will be 40% longer in another language.
  • Never hardcode currency symbols, date formats, or number formats — these must be dynamic.
  • Regulatory text varies per market; layouts must accommodate text blocks of unpredictable length.

UI principles

These sit alongside the UX principles and govern layout and interaction. They reference the V2 Dice Global Components design system by name; the design system remains the source of truth for component specs (spacing, colour, size).

14Don't stack banners or alerts

  • One message zone, one message. If several compete, show the highest-severity one (regulatory > error > warning > info) in a single DsAlert.
  • Never render two or more stacked alerts above the content — it pushes content down unpredictably and trains users to ignore the zone.

15One primary action per screen

  • Exactly one high-emphasis DsButton kind=primary per screen. Everything else is secondary or tertiary.
  • If a screen seems to need two primary actions, the screen is doing too much — that's a design question, not a build decision.

16Respect the established layout skeleton

  • Each surface has a fixed regional structure (header / message zone / content / sticky action). Changes slot into existing regions.
  • Adding a new region, moving the sticky action, or changing the skeleton is not a routine change — take it to design.

17Validation lives inline, under the field

  • Field-level validation uses the input's error state plus DsHelpItem type=error directly beneath the field.
  • The top message zone is for page- or system-level messages, not field errors.

18Match the message surface to severity

  • Inline DsHelpItem / DsAlert for field and page messages; DsModal (or Bottom Sheet) for soft checks that need a decision; full-screen for hard blocks.
  • Never downgrade a hard regulatory block to a dismissible banner, or upgrade a minor hint to a blocking modal.

19Equal weight for paired choices

  • When a choice has two outcomes (e.g. Cancel / Continue), both use the same DsButton weight — the protective or safer option is never visually de-emphasised.
  • This is the UI expression of UX principle 7 (no dark patterns).

20Use the design system component as-is

  • Build from the existing Ds component and its documented variants and states. Don't restyle, fork, or recreate a component to fit a one-off need.
  • If no existing component or documented variant fits, that's a signal the pattern doesn't exist yet — take it to design.

Applying these

  • Cross-check every screen against the UX principles; flag any violation in your output.
  • Build layout and components within the UI principles, using the design system by name.
  • When a change can't be expressed within these principles and the per-feature guidance, stop and take it to design rather than inventing a new pattern.
